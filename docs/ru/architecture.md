# Архитектура Partscaster
**Русский** · [English](../en/architecture.md)

Partscaster — это три программы: desktop-приложение (окно), MCP-сервер для AI-агентов и воркер
(сервер на машине с видеокартой NVIDIA, который генерирует музыку моделью YuE2). Приложение и MCP
ничего не генерируют сами: они ходят к воркеру по HTTP. Здесь — из чего они состоят и как связаны;
установка — в [deployment.md](deployment.md), API воркера — в [api.md](api.md), инструменты MCP — в [mcp.md](mcp.md).

## Общая схема

```
 ПК (Linux / Windows)                                Машина с NVIDIA (часто — тот же ПК)
┌──────────────────────────────┐   HTTP :8091    ┌─────────────────────────────────────┐
│ partscaster — приложение     │ ──────────────▶ │ воркер (Python, FastAPI, :8091)     │
│ Wails v2: Go + Vue 3         │                 │  • общая очередь к видеокарте       │
│  • звук — системный плеер    │                 │  • генерация YuE2 — yue2.cpp        │
│  • эффекты ffmpeg — локально │                 │    (yue-server на 127.0.0.1,        │
│  • пресеты звука, пересборка │                 │    запускает и гасит воркер)        │
├──────────────────────────────┤                 │  • SheetSage2, дорожки RoFormer     │
│ partscaster-mcp — MCP-сервер │ ──────────────▶ │  • звуковой движок, NAM, наборы     │
│ stdio, для AI-агентов        │                 │  • whisper, Seed-VC — отдельными    │
└──────────────────────────────┘                 │    окружениями (по желанию)         │
                                                 │  SQLite + файлы треков              │
                                                 └─────────────────────────────────────┘
```

- Приложение и воркер — отдельные процессы: закрытие приложения не прерывает генерации, очередь и
  треки живут на воркере (`<данные>/yue.db`, по умолчанию данные — `~/partscaster/data`).
- Воркер на Linux работает службой systemd (`partscaster-worker`), на Windows без WSL — программой
  `partscaster-worker.exe` (см. ниже).
- Адрес воркера у приложения и MCP один: переменная `PARTSCASTER_URL` → сохранённый адрес из «Настроек»
  приложения → `http://localhost:8091` (`internal/config`).

### Студия и пресеты звука (`internal/studio`)

Это общий для приложения и MCP код, который превращает правки трека в новую версию. Тяжёлое (модель,
разделение, звуковой движок, мастер) делает воркер, ffmpeg-обработку и сборку — ПК.

- **Пересборка** (`sections.go`, `splice.go`, `dspapply.go`, `envelope.go`): эффекты на дорожки, вклейки
  кусков, перерендеренных моделью, линия громкости, место дорожки в стерео. Пересборка всегда идёт от
  чистого `audio.flac` со всеми заменами; голос при вклейке инструментов не заменяется; мастер — последним
  шагом на воркере, рядом сохраняется «микс без мастера».
- **Пресеты звука** (`presets.go`): рецепт обработки готового трека. `ApplySoundPreset` получает дорожки
  (нет — разделяет; части барабанов — RoFormer), ставит нужные наборы сэмплов, делает пересборку правок
  «весь трек», финальную цепочку ffmpeg, мастер и громкость к цели на воркере и сохраняет результат версией
  трека; уровни сверяются по итогу. `RunGraph` — общий шаг «граф ffmpeg на файл трека → вариант».
  `PresetRunner` применяет пресеты, выбранные при создании трека, когда очередь видеокарты пуста.
- **Слой «живой звук»** (`livelayer.go`): добавляется к любому пресету — воздух выше 16 кГц и тарелки
  у пресетов с живыми наборами, барабанщик в припевах ([effects.md](effects.md)). В рецепт пресета не входит.
- **Партии** (`parts.go`): ноты синта по аккордам и удары перкуссии по тактам.
- **Рецепт трека** (`recipe.go`): импорт песни на другой установке — корень генерацией, затем записи
  журнала правок по порядку.
- **Операция очереди** (`queueop.go`): `RunOp` / `StartOp` — цепочка (пресет, пересборка) занимает одно
  место в общей очереди воркера, пока не закончится (см. «Общая очередь»).

Рецепты пресетов и статусы «пресет у трека» хранит воркер (таблица `sound_presets`), применяет — ПК.

## MCP-сервер (`cmd/partscaster-mcp`, `internal/mcp`)

`partscaster-mcp` — MCP-сервер (Model Context Protocol): даёт AI-агенту (Claude Code, Claude Desktop,
Codex) те же возможности, что у приложения. Транспорт — stdio, протокол — JSON-RPC 2.0 построчно.

- Ходит к воркеру тем же клиентом `internal/yue` и использует те же конвейеры `internal/studio`
  (пресеты, пересборка, эффекты) — результат совпадает с приложением.
- Инструменты (75) разложены по файлам: `tools_workflow.go` (генерация и треки), `tools_studio.go`,
  `tools_revoice.go`, `tools_fx.go`, `tools_presets.go`, `tools_library.go` (библиотека стилей),
  `tools_queue.go`, `tools_recipe.go`, `tools_install.go` (`doctor`, `install_worker`, `install_app`).
- Данные библиотеки (`internal/mcp/*.json`) — копии источников фронтенда, встроенные в бинарник;
  перегенерирует их `make mcp-data` (`tools/mcp-gendata.sh`, он же пишет `worker/fx_presets.json`).
- Скачанные файлы — в `PARTSCASTER_MCP_DIR` (по умолчанию `~/partscaster-mcp-downloads`).
- Вызовы в общей очереди помечаются источником «mcp» (в приложении — пометка «ИИ»); изменяющие вызовы
  пишутся в журнал правок трека.
- Предупреждения в ответах: воркер другого поколения API (`compat.go`) и MCP, собранный раньше своих
  исходников (`stale.go` + `internal/buildinfo`, отпечаток вшивает `make mcp` через `cmd/srchash`;
  в релизной сборке эта проверка выключена).

## Воркер (`worker/`, Python)

Воркер — FastAPI-приложение `yue_worker:app` на порту 8091 без аутентификации. Все модули лежат плоско
в `worker/`.

| Модуль | Роль |
|---|---|
| `yue_worker.py` | все эндпоинты, SQLite, цикл генераций, запуск сервера yue2.cpp, настройки (`<данные>/settings.json`), микс овердаба |
| `opqueue.py` | общая очередь долгих операций (ниже); чистый модуль без FastAPI и torch |
| `proclock.py` | межпроцессная блокировка файла на Linux и Windows |
| `engine_cpp.py` | движок генерации **yue2.cpp**: модели (закреплённые файлы и суммы), рекомендуемая модель по видеопамяти, запуск и остановка `yue-server`, перевод заявок, разбор ответа и журнала; из командной строки — `python engine_cpp.py download <модель>`, `installed <модель>`, `recommend [МиБ]` |
| `sheetsage.py` | SheetSage2: трек → ABC-партитура (для пиано-ролла и овердаба) |
| `abcparse.py`, `plancheck.py`, `arc.py`, `chordgrid.py` | разбор ABC в таймлайн; проверка изменённого плана; драматургия (нарастание, взрыв) поверх плана; сетка аккордов по тактам |
| `stems.py`, `sep_run.py` | разделение на дорожки: BS-Roformer-SW + DrumSep подпроцессом в отдельном окружении (`sep_run.py download` — веса при установке) |
| `fx_engine.py`, `fx_nam.py` | звуковой движок (цепочка блоков на numpy/scipy, без сдвига во времени); усилитель NAM |
| `drumsynth.py`, `kits_install.py` | синтез драм-машин и синт-басов; установка наборов сэмплов заранее |
| `guitarpart.py`, `guitarnotes.py` | партия гитариста по аккордам плана и разбор её на удары для блока `gtrnotes` |
| `presets.py`, `genres.py` | пресеты звука: проверка рецепта, встроенные пресеты, статусы у трека; жанровые пресеты из готовых цепочек (`fx_presets.json`) |
| `instruments.py`, `phrases.py`, `phrases/` | страница «Инструменты»: свои инструменты и короткие фразы для прослушивания |
| `recipe.py` | рецепт трека из строк `jobs` и журнала `job_ops` |
| `voice.py`, `seedvc_run.py` | «голос альбома»: Seed-VC отдельной программой из своего окружения |
| `whisper_run.py` | что поёт готовый трек (MCP `job_lyrics`); запускается интерпретатором отдельного окружения whisper |

Таблицы SQLite: `jobs`, `sound_presets`, `job_ops` (журнал правок), `recipe_imports`,
`fx_instruments`, `voices`.

Данные (`PARTSCASTER_DATA_DIR`): `jobs/<id>/` — `audio.flac`/`.mp3`/`.wav`, `score.abc`, `request.abc`,
`latent.npy` (25 кадров/с), `semantic.npy`, `metrics.json`, варианты `dsp-*`/`overdub-*`/`preview-*`/`stem-*.flac`;
`voices/`, `references/`, `transcribes/`; `fx/amps`, `fx/irs`, `fx/kits` —
захваты NAM, импульсные отклики, наборы сэмплов; `yue2cpp-models/` — модели yue2.cpp; `settings.json`.

Волна и спектрограмма считаются воркером и кэшируются рядом с аудио: `<файл>.peaks.json`,
`<файл>.spectrum.png` + `.spectrum.json`. Для волны ffmpeg не нужен, для спектрограммы — нужен
(без него эндпоинт спектра отвечает 503).

## Конвейер генерации YuE2

Стадии модели: план (ABC-партитура) → семантические токены (авторегрессия слева направо) →
латенты (flow-matching) → декодирование VAE кусками.

Следствия:
- **правка середины меняет хвост**: точечных правок нет, каждый вариант — полный пересчёт;
- **превью куска дешёвое**: латенты сохранены, кусок декодируется за секунды без генерации;
- **инструменты задаёт строка стиля**, а не партитура: в ABC только голоса Vocal и Ins.

## Движок генерации — yue2.cpp

Генерирует [yue2.cpp](https://github.com/ServeurpersoCom/yue2.cpp) на GGML: модель YuE2-3B в GGUF. Прежний движок
на PyTorch (пакет `yue2`) убран; библиотека torch в воркере осталась — на ней SheetSage2 и NAM, а дорожки (RoFormer),
whisper и Seed-VC работают в своих окружениях.

| Модель | Файл | Видеопамять на пике |
|---|---|---|
| `bf16` | 7,2 ГБ | ~10 ГБ |
| `q8` | 3,8 ГБ | ~8 ГБ |
| `q6` / `q5` | 2,9 / 2,6 ГБ | ~7,7 ГБ |
| экономный режим (`--max-seq 8192`, песня до ~3,5 мин) | — | ~4,5 ГБ (Q8) |

- Воркер сам запускает `yue-server` на 127.0.0.1 (свободный порт) при первой операции с моделью и держит его
  между генерациями; смена модели или режима — новый процесс к следующей генерации; нехватка видеопамяти —
  сервер останавливается целиком.
- Модель и экономный режим — настройки воркера `cpp_model`, `cpp_low_vram` (приложение, MCP `config_set`).
  Рекомендуемую модель для карты считает `engine_cpp.recommend` (единственное место порогов): от 11776 МиБ —
  `bf16`, от 9728 — `q8`, меньше или неизвестно — `q8` в экономном режиме. Это подсказка (`GET /config` →
  `cpp_recommended`), выбирает пользователь.
- Трек помнит свою модель (`jobs.engine` = `cpp-<модель>`; у старых треков прежнего движка — `""` или `torch`).
  **Сид между моделями не переносится** — получится другое исполнение. **Ноты переносятся**: продолжение
  и превью идут по `semantic.npy` / `latent.npy`, поэтому старые треки продолжаются на yue2.cpp.
- Операции с моделью: трек, свой план, драматургия, черновик, фрагмент, продолжение, только план, превью
  куска, отмена.
- Программа yue2.cpp и файлы моделей закреплены (коммит репозитория, ревизия GGUF и sha256): обновление
  чужого проекта не меняет звучание уже сделанных треков.

## Общая очередь (`worker/opqueue.py`)

Видеокарта одна, поэтому работает одна долгая операция («слот»), остальные ждут по месту в очереди.

- В одной очереди: генерации (место — `jobs.queue_pos`, переживает перезапуск), тяжёлые секции эндпоинтов
  (`gpu_queue` → `QUEUE.slot`: рендер, план, превью, дорожки, голос, whisper, SheetSage, эффекты с
  усилителем) и **операции клиентов** — цепочки приложения и MCP (пресет звука, пересборка), которые держат
  слот на все свои шаги.
- Шаги цепочки несут заголовок `X-Partscaster-Op` и в очередь повторно не встают; вложенные секции
  воркера (авто-дорожки после рендера, дорожки внутри эффектов) — тоже. Порядок захвата: слот, потом
  блокировка модели `_pipe_lock`.
- Операция клиента живёт на отметках «жива» (`POST /queue/ops/{id}/beat`): клиент пропал на 180 с —
  операция «прервана», слот переходит следующей.
- Отмена: ждущая снимается сразу; у идущей внешние процессы (RoFormer, Seed-VC, whisper, yue2.cpp)
  останавливаются, работа внутри процесса воркера (SheetSage, NAM, план) доделывает текущий шаг;
  итог — «отменено», запрос получает 409.
- Пауза и операции клиентов хранятся в памяти воркера: после перезапуска пауза снята, а клиент получает
  404 и показывает «прервано».
- Эндпоинты: `GET /queue`, `POST /queue/ops`, `/queue/ops/{id}/beat|finish|move|cancel`, `POST /queue/pause`.
  В приложении очередь видна в боковой панели (`queueView.js`); у MCP — `queue_list`, `queue_move`,
  `queue_cancel`, `queue_pause`. Клиентская сторона — `internal/yue/queue.go` и `internal/studio/queueop.go`.

## Видеопамять

- Модель генерации живёт в отдельном процессе `yue-server`, запущенном между генерациями: на пике BF16 ~10 ГБ,
  Q8 ~8 ГБ, экономный режим ~4,5 ГБ. Видеопамять для `/stats` и текста ошибки воркер узнаёт у `nvidia-smi`, а
  не через torch: CUDA-контекст в его собственном процессе занял бы память зря.
- SheetSage2 маленькая (сотни МБ) и тоже остаётся загруженной.
- Разделение: RoFormer — отдельный процесс, память освобождается с его завершением.
- Звуковой движок: захват NAM (десятки МБ) грузится на вызов через очередь; остальные блоки — на CPU.

## Дорожки трека (контракт)

Файлы `stem-*.flac` в каталоге трека:

- **основные** — `drums`, `bass`, `other`, `vocals`: в сумме дают трек. По ним считаются вклейки,
  пересборка, проверка голоса (`vocal_leak`);
- **подробные внутри «прочего»** — `guitar`, `piano`: уточнение `other`, в сумму не входят;
- **подробные внутри «барабанов»** — `kick`, `snare`, `toms`, `hh`, `ride`, `crash` (DrumSep): уточнение
  `drums`, в сумму не входят. Сбой DrumSep не роняет основное разделение — частей тогда нет. У треков,
  разделённых до перехода на RoFormer (Demucs), частей нет; студия предлагает «разделить подробнее».

Дорожки делает только BS-Roformer-SW (`stems.py` запускает `sep_run.py` интерпретатором `PARTSCASTER_SEP_PY`),
выбора модели нет. У RoFormer «прочее» не включает гитару и клавиши, поэтому `other` приложения = other +
guitar + piano модели, а остаток «трек − сумма основных» раздаётся дорожкам по их вкладу на частоте — сумма
точная. Нет окружения или RoFormer упал — ошибка «разделение на дорожки не удалось: …», запасного пути нет.
Поле `model` ответа и `stems_model` в `GET /version` — всегда `bs-roformer-sw`; установлено ли разделение —
`roformer_available` в `GET /config`.

## Воркер на Windows без WSL (`cmd/partscaster-worker`, `internal/workerexe`)

`partscaster-worker.exe` — одна программа, в которую при сборке пакета Windows вшит архив воркера
(`//go:embed payload`). Первый запуск ставит в папку пользователя (по умолчанию
`%LOCALAPPDATA%\partscaster-worker`) uv, Python 3.12, окружение и пакеты, окружение разделения на дорожки
(`sep-venv`, веса — в `sep-models`), распаковывает код воркера
в `app\` и запускает uvicorn; дальше — сразу запуск. Окно открыто — воркер работает: процесс Python
привязан к программе объектом задания Windows. Программа yue2.cpp — в архиве воркера (без неё пакет Windows
не собирается), модель генерации — в `data\yue2cpp-models\`, прочие веса — в `hf-cache\`, данные — в `data\`.
Подробности — [deployment.md](deployment.md).

## Сборка и релиз (`tools/`, `.github/workflows/`)

| Файл | Что делает |
|---|---|
| `tools/worker-tar.sh` | архив воркера `worker-<версия>.tar.gz`: код без тестов, `*.json`, `requirements*.txt`, скрипты установки, фразы, юнит systemd и готовая программа yue2.cpp для своей ОС (для Windows обязательна; Linux без неё — с предупреждением, `install.sh` соберёт сам) |
| `tools/release.sh` | пакет под ОС: приложение, `partscaster-mcp`, архив воркера, `INSTALL.txt`; для Windows — ещё `partscaster-worker.exe` |
| `tools/yue2cpp-build.sh`, `tools/yue2cpp-build.ps1` | сборка yue2.cpp: Linux — в контейнере CUDA 12.8, Windows — локально |
| `tools/mcp-gendata.sh` | данные библиотеки MCP из источников фронтенда |
| `deploy.sh` | `worker` — архив на GPU-машину и его `install.sh`; `build` — сборка приложения |
| `.github/workflows/ci.yml` | тесты и линтеры Go, фронтенда, воркера; сверка данных MCP с фронтендом (push в `main` и pull request) |
| `.github/workflows/release.yml` | по тегу `v*` — пакеты Linux, Windows, macOS и выкладка в GitHub Release |

Команды `make` и сборка по ОС — в [deployment.md](deployment.md).
