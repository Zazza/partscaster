# Рецепт трека: экспорт и импорт между установками

Статус: **реализовано** (октябрь 2026, этапы 1–3; zip-пакет §8 — нет). Документ — дизайн и почему так.

Отличия реализации от плана (по коду):

- **Журнал пишет приложение/MCP, не воркер.** Правки студии (пересборка, склейка, громкость, эффекты, пресеты)
  считаются на ПК и заливают на воркер готовый файл — воркер их параметров не видит. Поэтому все записи делает
  Go: обёртка API (`yue.Journaled`) — прямые изменяющие вызовы, операции студии — одной записью, глуша журнал
  своих внутренних шагов (иначе пресет при импорте повторился бы дважды). Воркер журнал только хранит
  (`POST /jobs/{id}/ops`).
- **Рецепт = корень + журнал по порядку** (`root` и `ops`, без отдельного списка `nodes`): узлы n2, n3… задают
  записи, создавшие трек (`result: job:nK`). id треков в params (parent_id, child_id, job_id, voice_src, head_id) и
  в именах файлов `overdub-<id>.flac` заменяются на n-id; ведущий импорта подставляет новые.
- **Импорт ведёт приложение (и MCP)**, как пресеты в фоне: воркер хранит сессию, состояние и захват (лиза 10 мин),
  ведущий (`studio.RecipeRunner`) — шаг за тиком; повтор после сбоя — с того же шага.
- Правка, ссылающаяся на трек вне песни (чужой кусок склейки), пропускается с предупреждением.
- В рецепте `durations` — длительности версий: импорт пишет в ход, если новая отличается больше чем на 2 %.

## 1. Задача и не-задачи

Перенос песни с одной установки Yue Studio на другую (другой компьютер, другой воркер)
**без перекачивания аудио**: маленький файл-«рецепт», из которого входящая сторона
воспроизводит трек заново.

Не-задачи:

- не бит-в-бит перенос готового звука (это противоположность идеи; если понадобится —
  см. §8, zip-пакет);
- не синхронизация библиотеки (пресеты/голоса/инструменты) между установками — только
  то, что нужно конкретному треку;
- не перенос корпусов (профилей исполнителя).

Ключевая формулировка для пользователя: **переносим правила, а не трек**. При импорте
создаётся новый трек, очень похожий на исходный. Эта фраза — везде в UI, без «переноса».

## 2. Принцип: три яруса воспроизводимости

| Ярус | Что | Гарантия |
|---|---|---|
| 1. Детерминированно | весь пост-процессинг: rebuild specs, DSP-цепочки, place/pan, envelope, сплайсы, пресеты | при том же входном рендере — идентичный результат (чистые ffmpeg/цепочки воркера над числами) |
| 2. Почти | сам рендер YuE: тот же `seed` + план + стиль + лирика | очень близкое исполнение, **не** бит-в-бит: GPU-недетерминизм, версия модели |
| 3. Невоспроизводимо текстом | тембр `voice_convert` (образец-аудио), импортированный чужой трек, кастомные NAM-захваты и IR | только zip-пакет с блобами (§8) |

Следствия:

- в рецепт пишется версия модели воркера; при несовпадении на входящей стороне —
  предупреждение при импорте («исполнение может заметно отличаться»);
- рецепт — это DAG операций, и каждая операция уже существует как эндпоинт воркера.
  **Импорт = replay тех же вызовов**, нового кода обработки звука не появляется.

## 3. Что уже сериализуемо сегодня (факты из кода)

Таблица `jobs` воркера (`worker/yue_worker.py`) уже хранит весь генезис трека:
`style`, `lyrics`, `seed`, `cot`, `req_abc`, `arc`, `max_tokens`, `temperature`, `cfg`,
`parent_id`/`role`, `overdub_of`/`overdub_gain`, `cont_from`, `voice_src`, `head_id`,
`folder`, `draft`.

То, что правится поверх рендера (варианты `dsp-*.flac`), сегодня — **только файлы
результатов** + `metrics.json`; параметры, которыми вариант получен, нигде не хранятся.
Это единственный системный пробел — закрывается журналом операций (§5).

`sound_presets`, `fx_instruments`, `voices` — уже JSON-структуры в БД.

## 4. Формат рецепта

Один файл `*.yue-track.json` (UTF-8, обычный JSON, десятки КБ; самое тяжёлое — ABC-план).

```json
{
  "format": "yue-track-recipe",
  "version": 1,
  "exported_at": "2026-10-11T12:00:00+03:00",
  "worker_model": "yue2-…",
  "track": {"title": "…", "folder": "Альбом", "head": "n3"},
  "nodes": [
    {"id":"n1","type":"generate","style":"…","lyrics":"…","seed":123,
     "cot":"full","arc":"","temperature":0,"cfg":0,"max_tokens":0,
     "plan_abc":"X:1…"},
    {"id":"n2","type":"render","parent":"n1","role":"rebuild",
     "abc":"X:1…","style":"…","seed":123},
    {"id":"n3","type":"variant","parent":"n1","voice_src":"n2"},
    {"id":"n4","type":"continue","parent":"n1","from_sec":95.2,
     "style_add":"…","seed":0}
  ],
  "ops": [
    {"node":"n3","op":"rebuild_sections","params":{"specs":[…]}},
    {"node":"n3","op":"volume_envelope","params":{"points":[…]}}
  ],
  "stems_model": "htdemucs"
}
```

### 4.1. Типы узлов (сериализуются из `jobs`)

| type | Откуда | Поля |
|---|---|---|
| `generate` | submit | style, lyrics, seed, cot, arc, temperature, cfg, max_tokens; `plan_abc` — фактический план (score.abc) из каталога джобы, справочно |
| `render` | render_abc / куски для вклейки | parent, role, abc, style, seed |
| `continue` | continue_job | parent, from_sec, style_add, seed, abc (если передавался) |
| `overdub` | overdub | parent (джоба-источник), style, lyrics, seed, gain, abc |
| `variant` | variant_track / revoice_apply / готовая версия | parent, voice_src (если был) |
| `import` | import_track | только маркер: узел невоспроизводим без zip-пакета; в чистом рецепте экспорт таких треков запрещает корень (см. §6) |

Черновики (`draft=1`) в экспорт не попадают.

### 4.2. Правила

- **Стабильные id узлов** (`n1`, `n2`, …) — локальные для документа. Ссылки `parent`,
  `voice_src`, узлы в `ops[].node` и `track.head` — только по ним. Свои id джоб на
  входящей стороне не переносятся.
- **`ops` — журнал правок по узлам** (§5) в порядке применения. `params` — ровно те же
  JSON, что принимают эндпоинты: ничего не переводим во «внутренний формат».
- **Пресеты по значению, не по id**: если правка исторически была `sound_preset_apply`,
  журнал уже содержит разложенные шаги (каждый вызов воркера), replay не зависит от
  таблицы пресетов входящей установки. Определения пресетов в рецепт не кладём
  (перенос библиотеки — отдельная будущая фича).
- **`stems_model`** фиксируется, потому что от roformer/htdemucs зависит доступность
  частей барабанов в rebuild specs.
- **Голос**: для сгенерированного голоса ничего отдельного не нужно — он часть рендера
  (сид). Карточки `voices` (params+seed) к воспроизведению трека не применяются
  автоматически и в рецепт не входят. `voice_convert` — ярус 3, только zip.

## 5. Журнал операций `job_ops`

Предпосылка всего экспорта правок. Все мутирующие эндпоинты воркера записывают
применённую операцию в БД.

```sql
CREATE TABLE IF NOT EXISTS job_ops (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  job_id INTEGER NOT NULL,   -- трек, к которому применена правка
  op TEXT NOT NULL,          -- rebuild_sections | dsp_apply | fx_apply | volume_envelope | splice | revoice_apply | variant_track | voice_convert | update | set_head
  params TEXT NOT NULL,      -- JSON параметров вызова, как в API
  result TEXT DEFAULT '',    -- итог: имя варианта / id новой джобы — для контроля реплея
  created_at TEXT NOT NULL
);
```

- Запись **после успешного применения** (упало — не пишем; реплей должен быть линейным).
- Журналируются эндпоинты воркера — тогда оркестрация приложения/MCP (например,
  применение пресета звука как последовательность вызовов) попадает в журнал сама,
  отдельного «слова» для пресетов не нужно.
- `make_stems` не журналируется: это кэш, воспроизводится автоматически.
- Старые треки (правки до появления журнала): экспорт генезиса возможен, правки
  теряются — при экспорте честное предупреждение «правки студии не сохранены
  (сделаны до версии X.Y)». Обратной силы журнал не имеет.

## 6. Экспорт

Обход DAG от корня песни: `parent_id` → `overdub_of` → `voice_src` (источник голоса
версии — тоже узел). Порядок узлов в `nodes` = порядок создания; `ops` в порядке
журнала. `head` — текущая основная версия.

Эндпоинт: `GET /jobs/{root_id}/recipe` → файл (Content-Disposition).

Отказы экспорта:

- в DAG есть узел `import` (чужой трек без сида) — 422 с пояснением «нужен zip-пакет»
  (когда §8 сделан) или «трек основан на импортированном аудио и не переносится»;
- корень — черновик.

## 7. Импорт = replay

### 7.1. Сессия импорта

Импорт долгий (генерация — очередь GPU), поэтому это фоновый процесс со статусом:

```sql
CREATE TABLE IF NOT EXISTS recipe_imports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  status TEXT NOT NULL,      -- running | done | error
  progress TEXT DEFAULT '',  -- «узел n2 из 5: рендер…»
  error TEXT DEFAULT '',
  root_job_id INTEGER,       -- созданный корень
  created_at TEXT NOT NULL,
  finished_at TEXT DEFAULT ''
);
```

Фоновый поток воркера: узлы по порядку — генерационные ставит в существующую очередь
джоб и ждёт готовности, правки применяет когда узел готов. UI/MCP опрашивают статус.

### 7.2. Режим воспроизведения генерации (решение при импорте)

- **по сиду** (по умолчанию): `generate` проигрывается тем же submit с тем же сидом —
  тот же путь, что и оригинал, максимально близкое исполнение;
- **по плану**: если версии модели разошлись (предупреждение при импорте), режим
  «воспроизвести по плану» — render_abc из `plan_abc`: композиция фиксируется нота в
  ноту, исполнение новое.

### 7.3. Маппинг и дрейф времени

- перед стартом строится таблица `node_id → новый job_id`;
- правки с окнами в секундах (`from`/`to`) применяются как есть: дрейф длительности
  нового рендера обычно доли процента; если длительность узла отличается от исходной
  больше чем на 2% — предупреждение в прогресс сессии (окна правок могли сместиться);
- ошибки узла — сессия в `error` с текстом; повторный запуск сессии продолжает с
  последнего готового узла (готовые узлы не перегенерируются).

## 8. Zip-пакет (этап 2, опционально)

`*.yue-track.zip` = `recipe.json` + `blobs/`:

| блоб | для чего |
|---|---|
| `blobs/voice-ref-<node>.flac` | окно-образец для voice_convert |
| `blobs/import-<node>.<ext>` | исходник импортированного трека |
| `blobs/assets/*.nam, *.wav` | кастомные NAM-захваты и IR |

Правила: лицензии пользовательских файлов — на совести экспортёра (как у
`fx_asset_upload`); при импорте блобы разкладываются по своим местам, узел `import`
становится обычным импортом, `voice_convert` — обычной конвертацией.

## 9. UI

- Карточка трека / меню студии: «Экспорт рецепта» (сохранить файл) и «Импорт рецепта»
  (выбрать файл → превью: название, число узлов, версия модели, предупреждения →
  «Импортировать»).
- Текст при импорте (ru): «По правилам этого трека будет создан новый трек. Исполнение
  будет очень близким, но не идентичным; правки звука воспроизведутся точно.»
  При несовпадении версии модели: «…исполнение может отличаться заметнее. Можно
  воспроизвести по плану (ноты те же, исполнение новое)» + переключатель.
- Прогресс: «Узел 2 из 5: рендер…» — те же строки, что в `recipe_imports.progress`.

## 10. Синхронные изменения (правила репозитория)

По правилу синхронного обновения, каждый PR с эндпоинтом несёт всё сразу:

- воркер: эндпоинт + журнал;
- Go: `yue.Service` + биндинг `App` + `api.js`;
- MCP: инструмент `recipe_export` / `recipe_import`;
- `docs/api.md`, `docs/mcp.md`, этот файл;
- CHANGELOG (`Unreleased`) + `frontend/src/releaseNotes.js` (ru+en).

## 11. Тесты (по спецификации, не по текущему поведению)

- воркер (unittest): каждый мутирующий эндпоинт пишет `job_ops` после успеха и не
  пишет при ошибке; экспорт строит ожидаемый DAG (parent/voice_src/overdub_of, head,
  порядок ops); импорт-реплей на моках очереди создаёт узлы в порядке зависимостей;
  отказ экспорта для import-узла и черновика; продолжение упавшей сессии.
- Go: маппинг ответов воркера в `yue.Service`.
- фронтенд (vitest): превью импорта показывает предупреждения; переключатель
  «по сиду / по плану»; тексты i18n ru/en.

## 12. Этапы

1. **PR-1 — журнал**: таблица `job_ops`, запись во всех мутирующих эндпоинтах, тесты.
   Пользовательских изменений нет.
2. **PR-2 — экспорт**: эндпоинт `GET /jobs/{root_id}/recipe` + `yue.Service`/биндинги/
   `api.js` + MCP `recipe_export` + кнопка «Экспорт рецепта» + доки/CHANGELOG.
3. **PR-3 — импорт**: сессии `recipe_imports`, фоновый replay, эндпоинт статуса +
   импорта, MCP `recipe_import`, UI с прогрессом и предупреждениями.
4. **PR-4 (опционально) — zip-пакет**: блобы для voice_convert / import-узлов / NAM+IR.

## 13. Риски и открытые вопросы

- **Сид и версия модели**: с обновлением YuE сид даст другое исполнение. Лечится
  записью версии модели в рецепт и режимом «по плану».
- **Старые треки**: правки до журнала невосстановимы — экспорт генезиса с предупреждением.
- **Дрейф длительности** рендера vs секундные окна правок — порог 2% и предупреждение.
- Открытые вопросы:
  - перенос библиотеки (пресеты/голоса/инструменты) отдельным файлом — сейчас вне скоупа;
  - нужно ли вкладывать в zip готовые аудио рендеров (режим «без перерендера») —
    сознательно отказались, это другой сценарий;
  - корпусы — вне скоупа.
